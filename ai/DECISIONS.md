## Принятые решения

### 2026-08-04 — Автоподбор модели Gemini через ListModels

**Проблема:** Хардкод имени модели Gemini в коде постоянно ломался: несуществующие имена (`gemini-3.6-flash`, `gemini-3.5-flash`) приводили к 404, а доступность моделей у Google меняется (preview-версии, новые релизы).

**Решение:** `resolveGeminiModel()` в `src/api/recommendations.ts` запрашивает `GET /v1beta/models?key=...`, фильтрует модели с `supportedGenerationMethods: generateContent` по паттерну `gemini-*-flash*` и выбирает лучшую по приоритету `gemini-3 → gemini-2.5 → gemini-2.0` (без lite). Результат кешируется в модульной переменной; при 404 кеш сбрасывается.

**Причина:** Модель всегда соответствует тому, что реально доступно конкретному API-ключу. Не нужно вручную править код при выходе новых моделей.

**Альтернативы:**
- Фиксированная константа модели — отклонено (ломалась дважды за один день)
- Перебор кандидатов с fallback при 404 — отклонено (лишние запросы, расход квоты на нерабочие имена)

**Последствия:**
- Один дополнительный GET-запрос ListModels при первом вызове за сессию
- В логах Metro видно выбранную модель и полный список доступных
- **Правило: НЕ хардкодить имена моделей Gemini в коде**

### 2026-08-04 — Ответ ИИ резолвится в карточки TMDB

**Проблема:** Рекомендации ИИ отображались голым текстом (название + причина), без постеров и без возможности открыть детали или добавить в библиотеку.

**Решение:** Каждое название из ответа ИИ ищется через `searchMulti` в TMDB; лучший результат выбирается с учётом года из подсказки ИИ (`pickBestMatch` в `RecommendationsScreen.tsx`), дубликаты отсекаются. Рендер — `SearchCard` с постером, тап открывает `MovieDetailsModal`.

**Причина:** Пользователь сразу видит реальные фильмы с постерами и может добавить их в библиотеку. Галлюцинации ИИ (несуществующие фильмы) автоматически отсеиваются — их нет в TMDB.

**Альтернативы:**
- Просить ИИ возвращать TMDB ID — отклонено (ИИ не знает актуальные ID, галлюцинирует)
- Оставить текст — отклонено (плохой UX)

**Последствия:**
- До 5 дополнительных searchMulti-запросов за одну подборку (параллельно через Promise.all)
- Если ИИ ответил, а TMDB ничего не нашёл — отдельное сообщение с подсказкой проверить ключ TMDB

### 2026-07-29 — SQLite как единственное хранилище

**Проблема:** Нужно хранить данные о фильмах локально без сервера.

**Решение:** Использовать `expo-sqlite` для всех данных (фильмы, заметки, настройки).

**Причина:** 
- Нет необходимости в аккаунтах и синхронизации
- Приложение должно работать офлайн
- Простота реализации и отладки

**Альтернативы:** 
- AsyncStorage — отклонено (нет сложных запросов)
- Firebase — отклонено (требует аккаунт, не офлайн)

**Последствия:** 
- Все данные на устройстве
- Экспорт/импорт через JSON
- Нет коллаборации между пользователями

### 2026-07-29 — Переключаемые AI providers

**Проблема:** Разные пользователи предпочитают разные AI сервисы.

**Решение:** Поддержка Gemini, OpenAI, Claude с переключением в настройках.

**Причина:**
- У пользователей есть ключи к разным сервисам
- Разное качество рекомендаций
- Резерв на случай недоступности одного из сервисов

**Альтернативы:**
- Только Gemini — отклонено (ограничение выбора)
- Автовыбор лучшего — отклонено (сложность, непредсказуемость)

**Последствия:**
- Таблица `provider_settings` в БД
- UI для ввода API ключей
- Валидация ключей при сохранении

### 2026-07-29 — TMDB как единственный источник данных о фильмах

**Проблема:** Откуда брать информацию о фильмах.

**Решение:** Только TMDB API.

**Причина:**
- Бесплатный и стабильный API
- Хорошее покрытие фильмов и сериалов
- Есть постеры, описания, рейтинги

**Альтернативы:**
- Кинопоиск API — отклонено (закрытый, платный)
- IMDB — отклонено (нет официального API)

**Последствия:**
- Зависимость от внешнего API
- Необходимость API ключа
- Кэширование в SQLite для офлайн-режима
